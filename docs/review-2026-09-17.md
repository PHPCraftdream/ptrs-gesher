## Ревью текущей правки

`ServerInfo::new` теперь интерпретирует пустой `TOR_PT_EXTENDED_SERVER_PORT` как отсутствие ExtORPort, сохраняя прежний разбор непустого адреса и проверку необходимого cookie path. Правка локальна и не меняет непустую ветку.

Новый тест использует serial guard для process environment и `EnvGuard` для восстановления изменённых переменных, в том числе при unwind. Проверяет пустой ExtORPort с обычным ORPort и непустой ExtORPort без обычного ORPort.

В этом проходе выполнено:

```text
CARGO_PROFILE_TEST_DEBUG=0 cargo test --locked -p ptrs-gesher-core --lib server_info_accepts_empty_extended_port -j 1
1 passed; 0 failed; 39 filtered out
```

Тест проверяет разбор конфигурации. Он не проверяет успешный обмен протоколом ExtORPort с Tor.

## Общий код

### PT17-01 — P2: передать ошибку listener из lifecycle вызывающему коду

Места: [фатальный accept](../crates/lyrebird/src/lib.rs#L682), [обработка JoinSet](../crates/lyrebird/src/lifecycle.rs#L75), [логирование ошибки](../crates/lyrebird/src/lifecycle.rs#L302), [возврат Ok](../crates/lyrebird/src/lifecycle.rs#L147), [main](../crates/lyrebird/src/main.rs).

**Механизм.** `client_accept_loop` теперь правильно возвращает Err при фатальном accept. Однако `drive` передаёт этот результат в `log_listener_result`, который только печатает предупреждение. После исчерпания listener set выбирается `ExitKind::ProxyClosed`, выполняется drain, затем возвращается `Ok(())`. Бинарный `main` также возвращает этот успешный результат.

**Сценарии.** При единственном listener его фатальный отказ приводит к успешному завершению процесса; supervisor с restart-on-failure может его не перезапустить. При нескольких listener один объявленный транспорт может окончательно исчезнуть, а остальные продолжают работать без восстановления утраченного listener. Паника listener аналогично только логируется.

**Граница.** Временные ошибки accept из распознаваемого списка действительно повторяются; этот пункт не переоткрывает исправленный transient-retry. Ошибка находится в передаче результата уровнем выше. Искусственное исчерпание системных ресурсов не выполнялось.

**Исправление.** Сохранить причину отказа до окончания обязательного cleanup и вернуть Err. Для нескольких listener явно определить политику: завершать run при потере объявленного транспорта либо восстанавливать listener. Regression: передать в `drive` JoinSet с task, возвращающей Err, проверить и завершение owned tasks, и итоговый Err; отдельно проверить normal cancellation.

### PT17-02 — P3: fsync файла не обеспечивает durability опубликованного identity

Места: [atomic_write_json](../crates/obfs4/src/lib.rs#L162), [write_statefile_to](../crates/obfs4/src/server.rs#L679), [сохранение нового effective state](../crates/obfs4/src/server.rs#L258).

**Механизм.** Временный файл синхронизируется через `sync_all`, затем `NamedTempFile::persist` заменяет конечное имя. После этого родительский каталог не открывается и не синхронизируется.

**Сценарий.** Linux/Android: сервер впервые создал identity либо изменил её override, вернул успешный build и раздал client params, затем произошёл сбой питания. Файловая система может не сохранить новую directory entry / rename. После старта с отсутствующим state сервер получит новую identity, а уже розданные параметры относятся к прежней; при обновлении может восстановиться старый state.

**Граница.** Атомарность для обычных читателей обеспечивается; это замечание о crash durability, не о torn JSON. Windows и power-loss эксперимент не проверялись.

**Исправление.** После успешного persist синхронизировать родительский каталог там, где это поддерживается; явно определить обработку ошибок durability. Проверить относительный путь без каталога (в этом helper нормализация пустого parent на `.` уже есть), не допустить регрессии прав доступа 0600.

## Дополнительные границы и исключённые подозрения

- `experimental-server` явно помечен незавершённым и выключен по умолчанию; существующий `unimplemented!` не выдан за новый production-дефект клиентского транспорта.
- Публичный `ServerInfo::connect_to_or` открывает обычный TCP, включая ветку extended address, и не выполняет SAFE_COOKIE. Реальный ExtORPort требует предварительного обмена аутентификацией перед OR-трафиком: [спецификация Tor](https://github.com/torproject/torspec/blob/main/ext-orport-spec.txt). Встроенный server path этого helper не использует и объявлен незавершённым; без доказательства обещания authenticated-stream это отмечено как ограничение API, а не отдельная P2-находка. Новый env-тест не доказывает поддержку server ExtORPort.
- В WebTunnel `Fallback` разрешает system DNS по явному контракту режима; это само по себе не дефект Strict. Проверены отдельные ветви Strict/Fallback и literal-IP.
- `resolve_target_addr` для obfs4 отклоняет domain через parser числового адреса; синхронный системный DNS из одного имени функции не предполагается.
- Проверенные IAT poll-loop обрабатывают запрос padding в том же poll; прежнее исключённое предположение о Pending без wake не переоткрыто.
- Возможное состязание некооперирующего внешнего writer после `ensure_statefile_unchanged` уже признано в коде как отсутствие CAS; отдельно не посчитано новым дефектом текущей env-правки.
