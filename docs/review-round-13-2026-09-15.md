## PT13-01 — P2: IAT ограничивает следующий poll_write, но не вывод буфера

Места: [poll_write](../crates/obfs4/src/proto.rs#L356),
[poll_flush](../crates/obfs4/src/proto.rs#L553).

Проверка таймера выполняется перед новым вызовом write. Один большой write
может упаковать много кадров и несколько раз сбросить Framed через poll_ready
до установки iat_delay_pending. Последующий flush также не ожидает IAT.
В результате границы вызовов приложения определяют задержки вместо отправок.

Диагностический carrier, делегирующий настоящему Tokio duplex, зафиксировал
для IAT Enabled, 16 384 байт payload и свободного буфера: 2 carrier writes,
все в одном виртуальном Instant, elapsed 0; payload получен полностью.
Это не замер быстродействия: замороженное время показывает отсутствие
ожидания таймера на пути вывода данных.

В [эталонном Write](https://github.com/Yawning/obfs4/blob/master/transports/obfs4/obfs4.go)
IAT разделяет вывод на порции с ожиданием между отправками. Это также проверено
в локально доступном исходнике закреплённого interop commit `c3e2d44b1033`.
Байтовый interop сам по себе такую разницу не обнаруживает.

Исправление: состояние отправки ciphertext, размер и таймер каждой порции;
flush должен проходить через тот же механизм. Сохранить backpressure и
корректный учёт принятого payload. Проверять время/размер carrier writes,
а не только факт установки внутреннего флага задержки. Фактическая проверка
этого раунда выполнена для mode 1; mode 2 использует общий путь, но отдельный
динамический сценарий для него здесь не запускался.

## PT13-02 — P2: statefile не совместим с числовым iat-mode Go

Места: [JsonServerState](../crates/obfs4/src/server.rs#L302),
[клиентский импорт](../crates/obfs4/src/client.rs#L41).

Обе структуры ожидают Option<String>. В
[Go jsonServerState](https://github.com/Yawning/obfs4/blob/master/transports/obfs4/statefile.go)
поле IATMode имеет тип int. Проверен и закреплённый исходник `c3e2d44b1033`.

Для валидного файла с `"iat-mode": 0` Server::new_from_statefile_at вернул
`invalid type: integer '0', expected a string`. Контрольный файл с теми же
ключами и строкой `"0"` загрузился. Собственная запись Rust также использует
строку, так что обычный Rust roundtrip не проверяет совместимость формата.

Исправление: числовая каноническая запись и совместимый reader для уже
созданных строковых файлов; независимо валидировать диапазон 0/1/2.
Добавить импорт настоящего Go fixture и проверку обратного направления.

## PT13-03 — P2: builder объявляет не те параметры, с которыми работает server

Места: [ServerBuilder::client_params](../crates/obfs4/src/server.rs#L163),
[ServerBuilder::try_build](../crates/obfs4/src/server.rs#L187).

Новый default builder имеет случайную identity. После statefile_path существующий
файл читается только внутри try_build в локальные переменные. Построенный Server
получает сохранённую identity, но сам builder остаётся прежним: client_params
и trait get_client_params кодируют его исходные значения.

Публичный сценарий подтвердил: server загружает правильную исходную identity,
но параметры builder не равны параметрам server как до, так и после build.
Клиент, настроенный опубликованными builder-параметрами, не сможет пройти
handshake с этим сервером. Не требуется гонка или повреждённый файл.

Исправление: одна материализованная effective configuration для build и
экспорта параметров. Предпочтительно разделить загрузку/валидацию и построение,
чтобы getter не выполнял неявный повторный I/O и не маскировал ошибку загрузки.
Regression: statefile → свежий builder → build → полученные через builder
параметры → реальный успешный handshake с построенным server.

## PT13-04 — P2: override ключей заодно заменяет не заданный node ID

Места: [try_node_keys](../crates/obfs4/src/server.rs#L88),
[слияние state](../crates/obfs4/src/server.rs#L201).

try_node_keys задаёт identity_override=true для private/public пары.
try_build при этом пропускает весь state_identity, включая node ID, даже
когда node_id_override=false. Остаётся случайный node ID default builder,
и затем он записывается поверх сохранённого. Это нарушает описанное в
[VALIDATION.md](VALIDATION.md) правило независимого override соответствующих полей.

Воспроизведено с заведомо разными node ID: после смены только ключевой пары
сохранённый ID не сохранился; записан именно исходный default ID builder.
Различие fixture обеспечено изменением одного бита, не вероятностным ожиданием.

Исправление: независимое слияние node ID, private/public pair, IAT и seed;
флаг ключевой пары не должен означать override всех полей identity.
Проверить все одиночные overrides и их сочетания, включая состояние на диске.

## PT13-05 — P2: ERROR не отсекает DEBUG внутри существующего span

Места: [ManagedLayer::new_span_filter](../crates/lyrebird/src/logging_layer.rs#L210),
[enabled](../crates/lyrebird/src/logging_layer.rs#L76),
[нынешний тест reload](../crates/lyrebird/src/logging_tests.rs#L224).

Каждый span хранит Arc старого EnvFilter. enabled выбирает этот фильтр по
current_span, а вложенные spans наследуют его. После перенастройки на ERROR
долгоживущая ветка span продолжает пропускать DEBUG/TRACE, хотя вне неё новый
уровень уже действует. При длительном root span это может продолжаться весь run.

Probe использует непосредственно исходный logging_layer.rs и тот же порядок
регистрации callsite/замены filter. Получено: debug до reload — true; debug
после ERROR внутри старого span — true; снаружи — false. Существующий тест
также явно ожидает DEBUG после ERROR внутри активного span, то есть закрепляет
это поведение вместо проверки нового порога.

Исправление: новый фильтр должен определять допуск новых событий; нужные
атрибуты активных spans следует сохранять/переигрывать отдельно. Если snapshot
policy намеренна, её необходимо явно выделить как иной контракт; сейчас
общий параметр уровня не является действующим общим порогом после reload.

## PT13-06 — P3: учёт abort handles стоит O(C) на каждое соединение

Место: [RunTasks::spawn_connection](../crates/lyrebird/src/lifecycle.rs#L235).

Перед каждым push выполняется retain по всем abort handles. При C живых
соединениях K новых поступлений требуют O(K·C) проверок is_finished и
удерживают общий std mutex, хотя JoinSet уже сообщает о завершившихся задачах.
Это не неограниченная утечка: admission cap 1024 сохранён. Замечание о стоимости
частых коротких соединений на фоне долгоживущих.

Исправление: адресуемый учёт по task ID и удаление при получении результата
JoinSet либо очистка с ограниченным бюджетом. Сохранить доступность abort
handles при занятом scheduler lock и защиту регистрации во время отмены.
Оценка по исходнику; ускорение wall-clock и профиль CPU не измерялись.

восстановления. Нужны узкие исправления и новые внешние оракулы.
